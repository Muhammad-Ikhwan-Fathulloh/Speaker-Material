Why Tokenization MattersMengapa Tokenisasi Penting

Saka handles Indonesian affixes (me-, per-, -kan) and punctuation correctly — not just a naive whitespace split. The LLM sees structurally meaningful units.

Saka menangani imbuhan Indonesia (me-, per-, -kan) dan tanda baca dengan benar — bukan sekadar split spasi. LLM melihat unit yang struktural bermakna.

Why Normalization Matters MoreMengapa Normalisasi Lebih Penting

Large models are trained on formal text. Normalizing slang locally improves the agent's comprehension accuracy and saves tokens — the representation becomes consistent across requests.

Model besar dilatih dengan teks formal. Normalisasi slang di sisi lokal meningkatkan akurasi pemahaman agen dan menghemat token — representasi jadi konsisten lintas permintaan.

The Actual State Machine

State Machine Sesungguhnya

Four states, capped at five iterations — with full execution trace logged for debugging and transparency.

Empat state, maksimal lima iterasi — dengan jejak eksekusi penuh dicatat untuk debugging dan transparansi.

01

Planning

Planning

User message arrives, normalized via Saka-NLP. The LLM reasons about intent and required tools.

Pesan pengguna diterima, dinormalisasi lewat Saka-NLP. LLM menalar intent dan tool yang dibutuhkan.

02

Tool Selection

Tool Selection

LLM emits an Action JSON with the tool name and input it wants to invoke.

LLM mengeluarkan Action JSON berisi nama tool dan input yang ingin dipanggil.

03

Execution

Execution

Python function actually runs — RAG search, KBBI lookup, or morphological analysis.

Fungsi Python benar-benar berjalan — RAG search, lookup KBBI, atau analisis morfologi.

04

Reflection

Reflection

LLM evaluates: is the info sufficient? If not → loop back (max 5 iterations).

LLM mengevaluasi: apakah info cukup? Jika belum → kembali ke Tool Selection (maks 5 iterasi).

12 · Serving 13 · 20

LLM Serving Challenges

Tantangan LLM Serving

Two core architectural challenges behind End-to-End LLM Serving.

Dua tantangan arsitektural utama di balik End-to-End LLM Serving.

Challenge 01

Prefill / Decode DecouplingPemisahan Prefill / Decode

Prefill is compute-bound — processes the whole prompt at once. Decode is memory-bound — generates tokens one at a time.

Mixed on one engine → head-of-line blocking: decode requests stuck behind heavy prefill. Splitting them boosts throughput. Digabung di satu engine → head-of-line blocking: permintaan decode terblokir oleh prefill berat. Memisahkan keduanya menaikkan throughput.
Challenge 02

Cross-step State & KV-cacheState & KV-cache Lintas Langkah

An agent calls the LLM repeatedly within one task. The server must manage KV-cache and state across steps — without memory ballooning or redundant computation.

Persistent KV-cache + deterministic checkpoints = no re-running prefill every turn. KV-cache persisten + checkpoint deterministik = tanpa prefill ulang setiap putaran.

13 · Optimizations 14 · 20

Three Real Optimizations

Tiga Optimisasi Nyata

Beyond the core architecture — these are actually implemented in the backend.

Di luar arsitektur inti — ini benar-benar diimplementasikan di backend.

Opt 01

Semantic Response CacheCache Respons Semantik

Compare query against semantic_cache. If cosine distance < 0.1 (>90% similar), return cached answer — without calling the LLM.

Bandingkan query ke semantic_cache. Kalau jarak kosinus < 0.1 (>90% mirip), kembalikan jawaban cache — tanpa panggil LLM.

Opt 02

Semantic Vector RetrievalRetrieval Vektor Semantik

Via pgvector — pulls top 3 relevant docs based on all-MiniLM-L6-v2 embeddings, injects into system prompt.

Via pgvector — ambil 3 dokumen paling relevan berdasarkan embedding all-MiniLM-L6-v2, suntikkan ke system prompt.

Opt 03

Conversation MemoryMemori Percakapan

In-memory multi-turn memory keeps the last 10 messages per conversation_id, so dialogue stays coherent.

Memori multi-turn in-memory menyimpan 10 pesan terakhir per conversation_id, supaya dialog tetap koheren.
